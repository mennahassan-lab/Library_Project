QUESTION 1: How much is each member borrowing?
==========================================================================================

Reasoning:
A LEFT JOIN is used starting from members (not an INNER JOIN) so that members
who have never checked out a book are still included in the result, with a
count of 0, instead of disappearing from the answer.

SQL Query:
SELECT m.member_id, m.first_name, m.last_name, COUNT(c.checkout_id) AS checkout_count
FROM members m
LEFT JOIN checkouts c ON m.member_id = c.member_id
GROUP BY m.member_id, m.first_name, m.last_name
ORDER BY m.member_id;

QUESTION 2: Which books match a chosen author pattern?
==========================================================================================

Reasoning:
Chosen pattern: authors whose name starts with the letter 'A' (SQL pattern 'A%').
This was picked because it returns more than one author (Adel Roushdy, Amina
Darwish, Aya Hafez), which makes it a more meaningful test of the pattern search
than a letter that matches only a single author.

SQL Query:
SELECT book_id, title, author
FROM books
WHERE author LIKE 'A%'
ORDER BY author, title;

QUESTION 3: What are the most popular books?
==========================================================================================

Reasoning:
Checkouts are joined to books on book_id, grouped per book, counted, sorted from
most to least borrowed, and cut to the top 5 with LIMIT.

SQL Query:
SELECT b.book_id, b.title, b.author, COUNT(c.checkout_id) AS times_borrowed
FROM checkouts c
JOIN books b ON c.book_id = b.book_id
GROUP BY b.book_id, b.title, b.author
ORDER BY times_borrowed DESC
LIMIT 5;

QUESTION 4: Who are the most active readers?
==========================================================================================

Reasoning:
An INNER JOIN is appropriate here (unlike Question 1) because the question is
specifically about members who HAVE borrowed books; members grouped, counted,
ranked highest to lowest, and cut to the top 10 with LIMIT.

SQL Query:
SELECT m.member_id, m.first_name, m.last_name, COUNT(c.checkout_id) AS books_borrowed
FROM members m
JOIN checkouts c ON m.member_id = c.member_id
GROUP BY m.member_id, m.first_name, m.last_name
ORDER BY books_borrowed DESC
LIMIT 10;

QUESTION 5: What does a neighborhood's activity look like further back in time?
==========================================================================================

Reasoning:
Chosen neighborhood: Maadi (it has the largest number of checkouts in the
database, so it comfortably has more than 20 records to look back through).
Checkouts are joined to members to filter by neighborhood, ordered by
checkout_date from newest to oldest, then OFFSET 10 skips the 10 most recent
records and LIMIT 10 takes the next 10 -- i.e. records 11 through 20.

SQL Query:
SELECT c.checkout_id, c.member_id, c.book_id, c.checkout_date, c.return_date
FROM checkouts c
JOIN members m ON c.member_id = m.member_id
WHERE m.neighborhood = 'Maadi'
ORDER BY c.checkout_date DESC
LIMIT 10 OFFSET 10;

REFLECTION: Web Page vs. API as a Data Source
==========================================================================================

The Reading Kickoff signups live on an ordinary HTML web page, not behind an API, and that
difference mattered in very concrete ways for this project:

- Structure had to be assumed, not trusted. An API returns data in a predictable, documented
  shape (e.g. consistent JSON fields with clear types). This page had no such contract -- the
  data existed only inside an HTML <table>, formatted for a person's eyes. Getting it into a
  usable form required parsing the HTML (finding the <table>, reading each <tr>/<td>) and
  converting text like "1104" into an actual integer member_id, something an API would have
  handed over already typed and ready to use.

- No guarantee of clean, valid data. Because the page's own text explains that "desk
  volunteers record these checkouts by hand," the values on it cannot be assumed to be as
  reliable as a database export. That expectation turned out to be correct: three member IDs
  on the page (1104, 1150, 1201) don't correspond to any registered member at all -- something
  that would be far less likely coming from a system that enforces referential integrity, like
  the library database does.

- Missing fields had to be reasoned about, not just read. The page has no checkout_id and no
  return_date column, because a return date genuinely doesn't exist yet for these checkouts.
  An API would typically either omit a field consistently across all records or supply a clear
  null; here, understanding *why* return_date was absent (books "not due back until the end of
  the summer") came from reading the surrounding prose on the page, not from the data itself.

For this project specifically, that distinction mattered because the Reading Kickoff data
could not be combined with the database checkouts through a query the way the members and
checkouts tables were (Stage 1) -- it had to be scraped, cleaned, and manually reshaped in
Python before it could sit next to the rest of the dataset as equivalent rows.
